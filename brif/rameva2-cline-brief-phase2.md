# Rameva 2 — техническое задание, этап 2: исправления и следующий слой защиты

## Контекст

Этап 1 выполнен: старое ядро и сервисы перенесены под namespace `System\`/`App\`, во всех файлах ядра и конфигурации стоит PHP Guard, добавлены guard-заглушки во всех подпапках, роутер строит белый список маршрутов из `pages/` и кэширует карту. По факту сделано шире, чем планировалось на первый проход: Honeypot и AntiBot не просто перенесены, а сразу подключены в жизненный цикл каждого запроса (`Honeypot -> AntiBot -> Router -> Controller -> Renderer`). Прежде чем наращивать функциональность дальше, нужно закрыть несколько мест, которые требуют исправления или проверки по факту, а не только по синтаксису — и один пробел, оставшийся с первого этапа.

## Часть A — исправить в уже написанном коде

1. **Guard — сделать безусловным.** Текущая форма `defined('RAMEVA_CORE') or (http_response_code(403) && exit);` полагается на то, что `http_response_code()` при установке кода вернёт истинное значение (предыдущий код ответа) — это не гарантированное поведение для контроля доступа. Если оно окажется ложным, `&&` не дойдёт до `exit`, и скрипт продолжит выполняться, несмотря на то что доступ должен быть запрещён. Замени эту конструкцию во всех файлах на две отдельные безусловные инструкции: сначала явно установить код ответа 403, отдельной следующей строкой — безусловный `exit`, без зависимости от возвращаемого значения предыдущего вызова.

2. **Заглушки директорий — явный 403 вместо статического 200.** `index.html` в подпапках (`system/Core`, `Helpers`, `Http`, `Rendering`, `Security`, `Services`, `app/Config`, `app/Modules`, `pages/`) останавливает листинг, но отдаёт обычный статический ответ с кодом 200 — это не явный отказ и выглядит иначе, чем стандартный 404, что само по себе слабый лишний сигнал сканеру. Замени каждый `index.html` на `index.php` с той же guard-логикой (после исправления по пункту 1), которая явно возвращает 403 и не выводит никакого содержимого.

3. **Поведенческая проверка живого цикла запроса.** Синтаксической проверки PHP CLI недостаточно для Honeypot и AntiBot — они теперь участвуют в обработке каждого запроса. Нужно подтвердить: обычный браузерный запрос проходит Honeypot и AntiBot без ложного срабатывания; инлайн-JS челленджа реально выполняется в браузере (не только присутствует в HTML) и успешно завершает проверку. Если для этого нужен реальный браузерный тест, а не только PHP CLI — выполни его или опиши точные шаги, чтобы это мог проверить Сергей.

## Часть B — конвенция pages/: один файл на страницу, без обёрточных папок

Отменяется более раннее решение про папку на каждую страницу. Вместо этого — прямое соответствие URL и файла, где последний сегмент пути — это имя файла, а не папки:

- `pages/index.html` — главная страница (`/`); `pages/index.php`, если есть, — её контроллер.
- `pages/about.html` — страница `/about`; `pages/about.php`, если есть, — её контроллер, переопределяющий поведение по умолчанию.
- `pages/company/info.html` — страница `/company/info`. Папка `company/` — это только группировка по пути, а не страница сама по себе.
- `pages/company/index.html`, если создан, — это страница `/company` (тот же принцип index-файла, что и для корня).
- `pages/company/company.php` — контроллер по умолчанию для всех страниц внутри `company/`, применяется, если у конкретной страницы нет своего одноимённого контроллера.

Правило разрешения контроллера, на каждом уровне вложенности: сначала ищется файл с тем же именем, что у страницы, в той же папке; если его нет — файл с именем родительской папки в этой же папке (контроллер раздела); если и его нет — страница рендерится как статический HTML без контроллера.

Отдельная папка на страницу не создаётся никогда, включая главную страницу. Никакие ресурсы (изображения, стили, скрипты, даже используемые только одной страницей) не кладутся в `pages/` — они всегда идут в `assets/`; `pages/` содержит только `.html` и `.php`.

**Суффикс URL.** В конфигурации задаётся суффикс адреса (по умолчанию — пустая строка; можно указать `.html`, `.php`, `.asp` или любую другую строку). Суффикс не связан с реальным расширением файла в `pages/` (там всегда `.html`/`.php`) — это только то, что видно в адресной строке (используется для SEO или маскировки, реализовано в старом роутере). Роутер отрезает настроенный суффикс от входящего пути перед поиском совпадения в `pages/`. Если суффикс задан не пустым, а запрос пришёл без него или с другим суффиксом — редирект 301 на канонический адрес с правильным суффиксом, а не показ страницы одинаково по обоим вариантам: иначе это создаёт дублирующиеся URL на один и тот же контент.

**Модули.** Если в `page.html` встречается `{{ module_name }}`, рендер подставляет вывод соответствующего модуля из `app/Modules/`. Модуль — не то же самое, что контроллер страницы: контроллер управляет всей страницей и данными для неё, модуль — самостоятельный, переиспользуемый на разных страницах кусок динамического контента (пример — вывод показаний датчика).

Перенеси уже созданную стартовую страницу из `pages/home.html`/`pages/home.php` в `pages/index.html`/`pages/index.php`, обнови роутер и кэш карты маршрутов соответственно.

**Помощники (Helpers)**
Если пользователю нужно добавить набор глобальных функций (например, для работы со строками, датами или массивами), используются хелперы. В системе уже есть system\Helpers для хелперов ядра. Мне кажется, стоит предусмотреть пользовательские хелперы. Предлагаю вариант: чтобы создать свой хелпер, пользователю достаточно написать файл в директории app/Helpers/ с суффиксом _helper.php (например, custom_helper.php). Сделай эту папку.

**События и Фильтры (Events & Filters)**
Используются, если пользователю нужно внедрить логику в сам жизненный цикл приложения. Filters (Фильтры) - аналог Middleware в других фреймворках. Позволяют выполнять код до или после того, как контроллер обработает запрос (например, проверка авторизации, логирование, CORS). Events (События) - позволяют выполнять код в определенные моменты работы системы без изменения ядра (например, сразу после отправки письма или при загрузке системы). Я думаю, эти папки тоже нужно предусмотреть в app/.


## Часть C — то, что не было сделано на этапе 1 и должно быть закрыто сейчас

1. **Обработка отсутствующего маршрута и внутренней ошибки.** Сейчас для запроса вне белого списка `pages/` обработка не описана вообще. Нужны системные страницы по умолчанию по той же файловой конвенции, что и обычные страницы — `system/Pages/404.html` и `system/Pages/500.html` (при необходимости `404.php`/`500.php` как контроллеры) — и приоритет пользовательского переопределения: если в `app/Pages/404.html` (или `.php`) есть своя реализация — используется она, иначе применяется системная по умолчанию.

2. **Чёрный список известных путей сканеров поверх уже готового белого списка.** Заранее известные пути (`wp-login.php`, `xmlrpc.php`, `.env`, `vendor/phpunit`, `.git` и подобные) должны обрываться немедленным 403 до того, как запрос дойдёт до Honeypot, AntiBot или роутера — это дешевле по ресурсам и не задействует более тяжёлую логику ради заведомо мусорного запроса.

3. **Простое ограничение частоты запросов по IP** поверх этого же чёрного списка: счётчик обращений за интервал времени, временная блокировка при превышении порога. Хранение состояния — в `storage/cache/`, механизм должен включаться и отключаться через конфиг.

**Дополнение к логике рендера**
Это не требование, но нужно учитывать следующую логику: раз ты в app/Pages положил переопределение системных страниц, то наверное логично в app/Layouts положить шаблоны и реализовать механизм их использования. Страницы в pages могут содержать header и footer, которые в случае наличия шаблона игнорируются при рендере. Не реализовывай эту логику, а просто учти ее.

## Критерий готовности этапа 2

Guard везде использует безусловный `exit`, не зависящий от возвращаемого значения. Все заглушки в подпапках — `index.php` с явным 403, без кода 200 и без листинга каталога. Страницы лежат по конвенции «один файл — одна страница» прямо внутри `pages/`, без обёрточных папок (`index.html` — главная и индекс раздела, `<имя>.html` — конкретная страница, `<имя>.php` — её контроллер, `<имя_папки>.php` — контроллер раздела по умолчанию). Если задан суффикс URL, запрос без него или с другим суффиксом получает 301 на канонический адрес. Запрос к несуществующему маршруту отдаёт корректную 404-страницу с учётом пользовательского переопределения из `app/Pages`. Запрос к известному сканерскому пути (например, `/wp-login.php`) обрывается 403 без обращения к Honeypot, AntiBot или роутеру. Повторные запросы с одного IP сверх порога временно блокируются.
