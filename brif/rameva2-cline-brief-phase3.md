# Rameva 2 — техническое задание, этап 3: механизмы вместо папок и закрытие проверок этапа 2

## Контекст

Этап 2 закрыл Guard, заглушки директорий, конвенцию `pages/`, канонический редирект по суффиксу, обработку 404/500 с пользовательским переопределением, чёрный список известных путей и ограничение частоты запросов — всё это сделано по спецификации и частично реально протестировано, не только линтером.

При этом появились новые папки `app/Helpers/`, `app/Events/`, `app/Filters/`, `app/Layouts/` — но пока только как защищённые пустые каталоги, без механизма за каждой из них. Отдельно осталась незакрытой поведенческая проверка AntiBot: механизм не протестирован в реальном сценарии, а просто отключён по умолчанию (`'enabled' => false` в `app/Config/Security.php`), что убирает риск ложных блокировок сейчас, но не подтверждает, что сам челлендж работает.

Этот этап — не новая функциональность поверх старой, а реализация того, для чего эти папки уже созданы, плюс закрытие двух зависших проверок.

## Layouts — самая важная часть этого этапа

Реализовать механизм, а не только структуру папок. Кратко, полная спецификация была дана раньше — здесь она подтверждается как обязательная к реализации:

- Разрешение имени шаблона: сначала ищется в `app/Layouts/`, если там нет — берётся из `system/Layouts/` (тот же приоритет, что и для `app/Pages/` поверх `system/Pages/`).
- Шаблон — полноценный HTML-документ со своим `<head>`, header, footer, содержащий плейсхолдер (например, `{{ body }}`), в который подставляется содержимое страницы. Шаблоны именованные, их может быть несколько (`default.html`, `landing.html` и т.д.).
- Какой шаблон использовать для страницы, указывает её контроллер или контроллер раздела; если ни один не указал шаблон — страница рендерится без него, как есть.
- Если для страницы указан шаблон и сама страница — полноценный HTML-документ (есть `<html>`/`<body>`), в шаблон подставляется только содержимое её `<body>`; собственные `<head>`, `<title>`, meta, header и footer файла страницы полностью игнорируются.
- Если шаблон не указан — извлечения не происходит, страница отдаётся полностью так, как есть. Системные страницы из `system/Pages/`, которые не были переопределены, используют шаблон по умолчанию из `system/Layouts/`. 

Нужен рабочий пример: одна существующая страница со своим шаблоном в `app/Layouts/`, чтобы поведение было видно на реальном запросе, а не только в коде. Можно использовать \pages\index.html.

## Helpers — автозагрузка

Любой файл `app/Helpers/*_helper.php` (по аналогии — `system/Helpers/*_helper.php` для хелперов ядра) должен автоматически подключаться до выполнения контроллера, а его функции — быть доступны глобально, без явного `require` в каждом контроллере. Пользователю для добавления своего набора функций достаточно положить файл с таким суффиксом в `app/Helpers/` — ничего больше настраивать не нужно.

## Filters — аналог middleware

Механизм выполнения кода до и/или после обработки запроса контроллером — для авторизации, логирования, CORS и подобного, без изменения ядра. Для этого этапа достаточно глобальных фильтров (применяются ко всем маршрутам), без назначения фильтров на конкретные маршруты — это можно добавить позже, если реально понадобится. Список фильтров и порядок их выполнения (до/после контроллера) задаётся в конфигурации. Похожий механизм есть в CodeIgniter 4 (`app/Config/Filters.php`) — можно ориентироваться на общую идею, но реализовать заметно проще, без группировки по маршрутам.

## Events — простой диспетчер

Механизм, позволяющий подписаться на именованное событие и вызвать всех подписчиков в определённый момент работы системы, без изменения кода ядра. Для этого этапа достаточно минимальной реализации: регистрация обработчика по имени события и вызов всех обработчиков при наступлении события. Нужно подключить хотя бы две реальные точки вызова в уже существующем коде — событие после успешной отправки письма в `MailService`, и событие при завершении загрузки системы в `Boot.php`/`Kernel`. Готовых обработчиков по умолчанию быть не должно — только сами точки вызова, чтобы ими можно было воспользоваться позже.

## Закрыть проверку AntiBot из этапа 2

Временно включить AntiBot в тестовых условиях и подтвердить реальным браузерным тестом: инлайн-JS челленджа действительно выполняется, при успешном прохождении выставляется подписанный cookie, и запрос с валидным cookie проходит дальше без повторного челленджа. Также проверить и явно описать поведение при провале проверки (блокировка, редирект или что-то ещё). После проверки — сознательно решить и зафиксировать, включён AntiBot по умолчанию в дистрибутиве или нет, а не оставлять его выключенным без объяснения.

## Поведенческая проверка Rate Limiter

Подтвердить реальным повторным запросом, что после превышения `max_requests` за `decay_seconds` действительно возвращается `429`, и что блокировка снимается по истечении `block_duration`, а не остаётся постоянной.

## Что сознательно не входит в этот этап

Автоматическая генерация `sitemap.xml`/`llms.txt` и модулей canonical/OpenGraph/Schema.org, Tripwire-мониторинг целостности `system/`, и реальное включение FormService/MailService в рабочий сценарий (например, форма обратной связи). Это следующий, четвёртый этап — после того как инфраструктура `app/` (Layouts, Helpers, Filters, Events) и оставшиеся с этапа 2 проверки будут закрыты и подтверждены.

## Правила работы

Как и на предыдущих этапах: объяснять предполагаемые изменения до массового применения, не рефакторить по пути то, что не относится к этому заданию, спрашивать при архитектурной неопределённости, а не додумывать функциональность самостоятельно.

## Критерий готовности этапа 3

Есть минимум одна страница, реально использующая шаблон из `app/Layouts/`, и видно, что её собственные `<head>`/header/footer не попадают в ответ. Функция из пользовательского `*_helper.php` вызывается из контроллера без явного подключения файла. Хотя бы один фильтр реально выполняется до контроллера на любом маршруте. Событие `mail.sent` (или аналогичное) реально вызывается после отправки письма и видно в тестовом обработчике. Поведение AntiBot подтверждено настоящим браузерным тестом, а не отключением, и решение о значении по умолчанию явно зафиксировано. Повторные запросы сверх лимита реально получают 429 и разблокируются по истечении заданного времени.
