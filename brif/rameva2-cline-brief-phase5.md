# Rameva 2 — техническое задание, этап 5: исправления после этапа 4 и Tripwire

## Контекст

Этап 4 выполнен на хорошем уровне — SEO/GEO-автоматизация реализована и реально проверена на живых запросах, генерация sitemap.xml/llms.txt подтверждена именно в момент компиляции карты маршрутов, а не на каждый запрос. Заодно исправлены два самостоятельных бага (экранирование HTML из хелперов в плейсхолдерах тела, демо-текст вместо реального описания в fallback). Есть один содержательный пробел и несколько мелких, которые нужно закрыть перед Tripwire.

## Часть A — исправить

1. **Канонический редирект должен работать и при пустом суффиксе, и только на существующую цель.** Сейчас `/about.html` отдаёт `200` вместо `301` на `/about`. Правило «запрос с суффиксом, не совпадающим с настроенным, получает редирект на канонический адрес» должно применяться симметрично: если настроенный суффикс — пустая строка (адрес без расширения — канонический), то ЛЮБОЙ суффикс на конце входящего адреса (`.html`, `.php`, что угодно) считается несовпадающим и должен редиректить на адрес без него, а не отдаваться напрямую. Иначе получаются два разных URL на один и тот же контент, что и должен был предотвращать этот механизм.

   Отдельно: перед тем как выполнять 301, нужно убедиться, что канонический адрес реально резолвится в существующий файл — иначе получается «редирект в никуда» с последующим 404 на следующем запросе, лишний прыжок. Резолвер и так уже ищет файл на диске, чтобы выбрать страницу — эту проверку нужно делать до решения редиректить, а не после. Суффикс при этом всегда приклеивается к логическому имени маршрута, а не к реальному имени файла: `pages/company/index.html` отвечает на `/company`, и суффикс (если включён) добавляется к «company», а не к слову «index» — тогда «`/company` без суффикса» и «`/company` как папка» никогда не конкурируют, это один и тот же случай. Ориентируйтесь на переданный `Router.php` из старого фреймворка (оригинал лежит по адресу D:\OSPanel\home\fw.loc\app\Router.php) — там уже реализована именно эта модель (суффикс снимается и приклеивается один раз, без циклов, отдельной функцией `buildCanonicalPath`), только это MVC-роутер по контроллер/экшен, а не по файлам `pages/` — логику стоит перенести, а не резолюцию.

2. Убрать демо-хвост «— Пользовательский шаблон» из `<title>` в `app/Layouts/main.html`, чтобы `<title>` и `og:title` не расходились.
3. Удалить `public/storage/test_quick_rate.php` — лишний файл от более ранних тестов.
4. **Заменить `system/Services/Schema.php` на адаптацию старого `app/Core/Schema.php`, а не дописывать новый.** Старый файл (в старом фреймворке оригинал лежит в D:\OSPanel\home\fw.loc\app\Core\Schema.php) полнее того, что написано с нуля на этапе 4: там уже есть builder-паттерн, нормализация URL/дат/адреса, валидация обязательных полей по типу и фабрики `organization()`, `person()`, `product()`, `breadcrumbList()`, `webSite()`, `localBusiness()` — этого нет в текущей версии. Перенести namespace на `System\Services\Schema`, сохранить весь функционал, и добавить к нему `howTo()` и поддержку `speakable` — это то новое, что есть в текущей версии и чего нет в старом файле. Не писать эти фабрики заново, если старый код после проверки на актуальность работает.
5. Добавить в `robots.txt` строку `Sitemap:` с полным адресом `sitemap.xml` — адрес должен браться из конфигурации/текущего домена, а не быть захардкожен.
6. **Подавлять заголовок `X-Powered-By` на уровне приложения.** В старом `Controller.php` (D:\OSPanel\home\fw.loc\app\Controller.php) перед рендером вызывается `header('X-Powered-By: -')` — это перезаписывает заголовок, который PHP выставляет сам (`expose_php`), без необходимости лезть в php.ini на сервере. Перенести этот вызов туда, где сейчас формируются остальные заголовки ответа (`SecurityHeadersFilter`).

## Часть B — Tripwire: мониторинг целостности system/

Только обнаружение и уведомление, без автоматического восстановления — восстановление из встроенной копии само по себе риск цепочки поставок, если эта копия может быть подменена.

1. **Эталонный манифест.** При установке (или по явному запуску отдельного скрипта/маршрута администратора) сканируются все файлы внутри `system/` и для каждого считается SHA-256. Результат — не файл в открытом виде, а PHP-файл, возвращающий массив (`storage/integrity.manifest.php`), защищённый тем же Guard, что и остальная конфигурация — по той же причине, по которой конфигурация не хранится как `.env`.
2. **Периодическая проверка.** Пересчитывать хэши на каждый запрос нельзя — слишком дорого. Нужен отдельный скрипт/маршрут, который админ подключает через планировщик задач своей панели (в ISPmanager это раздел «Планировщик CRON» — сам Rameva не может создать себе расписание, он может только предоставить точку входа для внешнего вызова). Сравнение — файл за файлом с манифестом: изменён, удалён, добавлен новый.
3. **При расхождении** — событие пишется в отдельный `storage/logs/integrity.log` (не смешивать с обычным логом приложения). Отправку уведомления администратору можно реализовать через уже существующий `MailService` — это не то же самое, что «включение форм в рабочий сценарий» из следующего этапа, а обычное использование уже готового сервиса по его прямому назначению.
4. Область действия — только `system/`. Папки `app/`, `pages/`, `assets/` меняются пользователем в обычной работе, и их не нужно отслеживать — это будет только шумом ложных срабатываний.

## Критерий готовности этапа 5

Запрос к `/about.html` (и к любому другому адресу с посторонним суффиксом при пустом настроенном суффиксе) получает `301` на канонический адрес без расширения, но только если этот адрес реально резолвится в существующую страницу — иначе сразу `404`, без редиректа. `<title>` шаблона не содержит демо-текста. Лишнего тестового файла в `storage/` нет. `Schema.php` — адаптация старого файла с сохранёнными `organization()/person()/product()/breadcrumbList()/webSite()/localBusiness()` и добавленными `howTo()`/`speakable`. `robots.txt` указывает на `sitemap.xml`. Заголовок `X-Powered-By` подавлен на уровне приложения независимо от настройки `expose_php` на сервере. Манифест `system/` строится и хранится как защищённый Guard PHP-файл; отдельный скрипт проверки реально обнаруживает подмену/удаление/добавление файла в `system/` при ручном тестовом изменении и пишет об этом в `storage/logs/integrity.log`; автоматического восстановления нет.
