# Rameva 2 — бриф этапа 8D: исправление защитного контура

Это задание на исправления по результатам независимой проверки кода. Новых функций в этапе нет. Все пути указаны относительно `public/`. Сайты `fw.loc` и `wwbridge.loc` не трогать.

## Правила работы (обязательны)

1. Меняй только то, что названо в пункте. Никаких переписываний файлов целиком и «улучшений по пути».
2. Не создавай копии `*.bak`, `*.old`, `*.orig` внутри `public/`. Резервные копии допустимы только вне `public/` (например `../backup/`).
3. Каждый изменённый PHP-файл проверь `php -l`. Весь вывод команд приводи в отчёте дословно, без пересказа.
4. В отчёте для каждого пункта одно из трёх: PASS (с выводом команды), FAIL (с причиной), NOT RUN (с причиной). Слова «выполнено» без вывода команды не принимаются. Не пиши, что проверено то, что не запускалось.
5. Не записывай в отчёт значения ключей (`installer.key`, `integrity.token`, пароли SMTP).
6. Если пункт противоречит коду так, что нужно менять больше заявленного, остановись и опиши конфликт, не решай сам.
7. После всех правок: `cron.php … action=build` для пересборки манифеста, затем `action=check` — вывод в отчёт.

## A. Установщик: защита определяется сервером, не браузером

**A1.** В `Kernel::handleInstallerAction`, действие `finalize`: игнорировать `posture` и `diagnostics` из запроса. Сервер сам вызывает диагностику и проверку защиты, сам вычисляет статус и записывает результаты в `installer.state.php` (поле `diagnostics` не должно быть пустым). Запрос с `posture=secure` при не пройденной проверке должен получить `degraded` с причиной.

**A2.** `Installer::verifyProtection()`: статус «защита подтверждена» только если закрыты **все** проверяемые пути, а не хотя бы один. Список путей расширить непубличными расширениями: создать во время проверки временные файлы-пробы `storage/_probe.log`, `storage/_probe.json`, `pages/_probe.html`, `app/_probe.txt`, запросить каждый по HTTP, затем удалить пробы (удаление в `finally`). Проба доступна по HTTP с кодом 200 → путь открыт.

**A3.** Добавить проверку исполнения PHP в `assets/`: создать временный `assets/_probe.php`, выводящий случайную метку, запросить по HTTP, удалить. Метка в ответе означает, что PHP исполняется в `assets/`. Это не провал установки, но блокирует статус `secure`: итог `degraded` с причиной «PHP исполняется в assets/» и подсказкой (правило для Apache `.htaccess` или Nginx из `deploy/`).

**A4.** `secure` невозможен при `debug=true` или `environment != production` в `app/Config/App.php`. Причина в `degraded_reason`.

**A5.** Результаты каждой проверки (путь, код ответа, итог) сохранять в `diagnostics`.

Проверка: `tests/security_matrix.php` (см. раздел I) содержит сценарии «поддельный finalize с posture=secure», «Nginx без правил: проба открыта → degraded», «debug=true → degraded».

## B. Точки входа и Guard

**B1.** `index.php` и `cron.php` определяют `RAMEVA_CORE` сами, перед подключением `system/Boot.php`.
**B2.** `system/Boot.php` не определяет константу, а при её отсутствии завершает работу ответом 404 без тела.
**B3.** `app/Config/Mail.php` получает стандартный Guard, как остальные конфиги.
**B4.** Проверка: GET `/system/Boot.php` возвращает 404 без выполнения ядра (подтвердить тем, что в `security.log` и `app.log` нет новых записей Kernel).

## C. Кэш, лимитер, сессии, логи: сбор мусора

**C1.** `RateLimiter`: счётчики окон хранить не отдельными файлами на каждый IP и окно. Допустимо: один шард-файл на префикс ключа (например 16 файлов) с записью под `flock` и удалением просроченных записей при каждой записи. Общее число файлов лимитера ограничено константой, независимо от числа IP.
**C2.** `Cache::gc()`: удаляет истёкшие `*.cache.php` и все файлы `*.cache` без `.php` (старый формат). Не трогает `index.php`, `routes.php`, `assets.php`, `routes.signature.php`.
**C3.** `cron.php`, новое действие `action=gc`: вызывает `Cache::gc()`, удаляет файлы сессий старше `session_gc_maxlifetime`, удаляет ротированные `*.bak` логов старше 30 дней. Выводит число удалённых файлов.
**C4.** Дополнительно `Cache::gc()` вызывается из `Boot.php` после ответа с вероятностью 1 к 200 и не чаще раза в 10 минут (метка времени в файле под Guard).
**C5.** `Cache::get()`: убрать лишний `file_get_contents`.

Проверка: скрипт генерирует 2000 запросов с разных IP (подмена через `trusted_proxies` в тестовом конфиге или прямой вызов `RateLimiter` из CLI) и печатает число файлов в `storage/cache/` до и после `action=gc`.

## D. Tripwire: строгая проверка посторонних файлов

**D1.** В `assets/` и `storage/uploads/` разрешённый `index.php` проверяется по содержимому: размер не более 200 байт и совпадение с эталонной заглушкой (хэш в манифесте). Иное содержимое — событие `stray_php`.
**D2.** Расширения исполняемых файлов расширить: `php`, `phtml`, `phar`, `php3`, `php4`, `php5`, `php7`, `php8`, `pht`, `phps`, `inc`.
**D3.** Новое событие `stray_sensitive`: в корне сайта и в `assets/` найдены файлы `*.bak`, `*.old`, `*.sql`, `*.zip`, `*.tar`, `*.gz`, `*.log`, `*.ini`, `*.env`. Только запись в `integrity.log` и уведомление, без удаления.
**D4.** Правило для Cline: любая резервная копия внутри `public/` будет считаться инцидентом.

## E. Глобальная обработка ошибок

**E1.** В `Boot.php` зарегистрировать `set_exception_handler`, `set_error_handler` (для E_WARNING и выше пишет в `app.log`) и `register_shutdown_function` для фатальных ошибок. Посетитель при `debug=false` получает страницу 500 без деталей; при `debug=true` — как сейчас.
**E2.** Обработчики не должны выводить пути и сообщения в ответ при `debug=false`.

## F. Чёрный список и приманка

**F1.** Чёрный список сравнивает по сегментам пути, а не по подстроке: паттерн совпадает с целым сегментом или с началом сегмента, если паттерн заканчивается на `*`. `pma` убрать, `phpmyadmin` и `pma/` оставить как сегменты. `.env` — сегмент, начинающийся с `.env`, а не подстрока. `.git` — сегмент `.git`, не `.github`.
**F2.** Порядок в `Kernel::launch`: пути из `Honeypot::$wpProbePaths` обрабатываются приманкой **до** чёрного списка, если `honeypot.fake_wp = true`. Чёрный список остаётся для `.env`, `.git`, `vendor`, `composer.*`, резервных копий и т.п. При `fake_wp = false` поведение прежнее (403).
**F3.** Пропуск по User-Agent «SEO-ботов» не должен отменять обработку probe-путей: запрос к `/wp-login.php` с UA `Googlebot` получает приманку или 403, как любой другой.
**F4.** Фальшивые ответы приманки не добавляют `X-Powered-By` с версией PHP: заголовок остаётся `-`, как у остального сайта.
**F5.** Обновить `tests/server_check.php`: при `fake_wp=true` ожидается 200 для `/wp-login.php`, 403 для `/.env`.

## G. Определение IP и прокси

**G1.** `ClientIp`: `trusted_proxies` поддерживает CIDR (`10.0.0.0/8`, `127.0.0.1`, `::1`). Настройка переезжает в `app/Config/Security.php` (`trusted_proxies`); чтение из `Mail.php` и `Local.php` остаётся как запасной вариант.
**G2.** Результат вычисляется один раз за запрос (статический кэш), файлы конфигурации не перечитываются.
**G3.** `SessionService`: флаг `Secure` по `X-Forwarded-Proto` учитывается только если `REMOTE_ADDR` входит в `trusted_proxies`.

## H. Ключ cron и AntiBot

**H1.** `cron.php` принимает ключ в заголовке `X-Rameva-Key` или аргументом CLI. Передача в строке запроса остаётся, но помечается устаревшей: в `security.log` записывается предупреждение, пример команды в установщике показывает заголовок.
**H2.** `AntiBot` использует для подписи токена ключ установки (HMAC от `InstallationKey`), а не `secret_key` из `Security.php`. Параметр `secret_key` удалить из конфигурации.
**H3.** `app/Config/Local.php` исключить из архивов поставки и из Tripwire-проверки как пользовательский файл; в `.gitignore` оставить.

## I. Производительность маршрутов

**I1.** `Router`: проверку подписи источников (`pages/`, `assets/`, `app/Config/`) выполнять не чаще раза в N секунд. Параметр `route_check_interval` в `App.php`: по умолчанию 0 при `debug=true` и 60 при `debug=false`. Метка последней проверки хранится в файле под Guard. `cron.php action=routes` принудительно пересобирает карту.
**I2.** При `debug=true` карта не пересобирается на каждом запросе, а подчиняется тому же интервалу (0 = проверять сигнатуру на каждом запросе, перестраивать только при изменении).

## J. Nginx: конфиг и проверки

**J1.** `deploy/nginx/rameva2-server-block.example.conf`: добавить `try_files $uri =404;` в блок `location ~ \.php$`; запретить исполнение PHP в `assets/` и `storage/uploads/` отдельными `location ^~` с `return 404`; запретить `~* \.(bak|old|orig|sql|log|ini|zip|tar|gz|7z|rar|swp)$` (404); исправить устаревшие комментарии про `public/.htaccess`.
**J2.** `Installer::nginxSnippet()` генерирует тот же набор правил, что файл из `deploy/`. Источник один: файл читается из `deploy/` или правила собираются в одном месте.
**J3.** Добавить `deploy/nginx/proxy-to-apache.example.conf` для схемы «Nginx проксирует на Apache» (статика отдаётся Nginx, остальное идёт на Apache).

## K. Тесты безопасности (новый файл `tests/security_matrix.php`, CLI-only)

Параметры: `BASE_URL`, `ROOT`, `MODE` (`apache`, `nginx`, `proxy`). Сценарии:

1. Прямые запросы к `system/`, `app/`, `storage/`, `pages/`, `tests/`, `deploy/`, `.git/`, `.env`: код 403/404 **и** тело не содержит PHP-кода и фрагментов `<?php`.
2. Варианты пути: другой регистр (`/System/Boot.php`), `%2e%2e/`, двойное кодирование (`%252e`), завершающая точка, `//`, `/index.php/x`, `/assets/../system/Boot.php`.
3. Пробы по расширениям из A2 (создаёт и удаляет временные файлы).
4. Исполнение PHP в `assets/` (проба из A3).
5. Подделанный `finalize` (A1), `debug=true` (A4).
6. Приманка: `/wp-login.php` при `fake_wp=true` отдаёт 200 и нет `X-Powered-By` с версией; с UA `Googlebot` результат тот же.
7. Чёрный список: `/pmarket` → не блокируется, `/.github/x` → не блокируется, `/.env` → блокируется.
8. Сбор мусора (раздел C): число файлов до и после.
9. Tripwire: подложить `assets/index.php` с кодом → событие `stray_php`; подложить `assets/x.bak` → `stray_sensitive`; удалить после теста.
10. Обработка ошибок: временно вызвать исключение вне блока рендера → ответ 500 без деталей, запись в `app.log`.

Критерий PASS для «закрытого» пути: статус строго 403 или 404. Пустое тело при статусе 200 — FAIL. Тест не должен менять состояние сайта; созданные временные файлы удаляются в `finally`.

Прогон: на Apache (текущий OSPanel), на Nginx+PHP-FPM и на схеме Nginx→Apache. Если режим недоступен, пометь NOT RUN с причиной, не подменяй другим.
