# Rameva 2 — техническое задание: миграция ядра и первый этап разработки

## Контекст

Rameva 2 — самостоятельный PHP-фреймворк для быстрого и безопасного развёртывания лёгких сайтов, в том числе сгенерированных ИИ-агентами, на обычном shared-хостинге (типично — панели вроде ISPmanager, где document root жёстко привязан к папке, куда заливаются файлы, а доступа к конфигурации Apache/Nginx у пользователя нет). Разработку ведёт один человек, поэтому главный принцип — не переусложнять: система должна быть проще, чем Symfony или Laravel, ориентирована на функциональность и кодовую базу CodeIgniter 4, но не копирует его модель обновления через Composer — ядро (`system/`) обновляется целиком перезаливкой папки, без `vendor/`.

Целевой пользователь фреймворка — не разработчик: он копирует файлы на хостинг и не разбирается ни в SEO, ни в Schema.org, ни в настройке веб-сервера. Поэтому всё, что можно сделать автоматически (маршрутизация, sitemap.xml, llms.txt, canonical/OpenGraph/Schema.org, защита от прямого доступа к файлам), должно работать без его участия.

## Текущее состояние

Старый фреймворк (первая версия Rameva) содержит рабочий код: Router, Db, Kernel, антибот-модуль с фингерпринтингом (Canvas/WebGL/AudioContext) по образцу Qrator, Honeypot, Canonical, Schema, Cache, FormService, LogService, MailService и другие сервисы — его нужно перенести и адаптировать, а не переписывать с нуля. Он лежит по адресу D:\OSPanel\home\fw.loc, проверь прежде чем переносить что-либо.

Новая структура уже создана локально (OSPanel, домен `fw2.loc`, обслуживается из папки `public`):

```
index.php, llms.txt, robots.txt, sitemap.xml
app/{Config, Modules}
assets/{css, images, js}
pages/
storage/{cache, debugbar, logs, session, uploads}  — с .htaccess и index.html-заглушками
system/{Boot.php, Core, Helpers, Http, Rendering, Security, Services}
```

Это целевая раскладка — она не меняется, работа идёт внутри неё.

## Принятые архитектурные решения (не пересматривать в этом проходе)

**Развёртывание — два профиля, не один.** Часть панелей хостинга (подтверждено на ISPmanager 6) позволяет задать «публичную директорию сайта» отдельно от корня сайта: тогда `system/`, `app/`, `storage/`, `config/` можно вынести за пределы того, что реально отдаёт веб-сервер, и они физически недоступны по HTTP — это protected-профиль, аналог `Config\Paths.php` в CodeIgniter 4. Но это поле не включено по умолчанию: если его не задать, публичная директория совпадает с корнем сайта, и получается тот самый плоский режим, который сейчас развёрнут в `fw2.loc`. На объём этого прохода это не влияет: PHP Guard и защита на уровне PHP нужны в обоих случаях — как основная защита в плоском режиме и как дополнительный рубеж в защищённом. Единственное требование: не зашивать в bootstrap и роутер жёсткое предположение «`index.php` всегда на одном уровне с `system/`» — путь к корню проекта должен вычисляться, а не быть захардкожен, чтобы позже добавить вариант с `public/index.php` без переписывания этой части.

**Модель страниц — только runtime, без офлайн-компилятора.** Каждая страница — папка внутри `pages/` с файлом `page.html` и, опционально, `controller.php`. Оба обрабатываются на каждый входящий запрос: контроллер (если есть) готовит данные, `page.html` (под page имеется ввиду имя конкретной страницы) рендерится с подстановкой плейсхолдеров. Отдельного шага «сборки» перед публикацией нет — это лишняя инфраструктура для одного разработчика и источник рассинхронизации между исходником и скомпилированным файлом. Производительность на продакшене обеспечивается кэшированием карты маршрутов и, при необходимости, кэшированием результата рендера в `storage/cache/` — а не отдельным build-шагом.

**Объём этого прохода — только фундамент.** Не нужно за один раз реализовывать всю систему безопасности, SEO-модули и полноценный движок вёрстки. В этот проход входит:

1. Перенос старого ядра и сервисов в новую структуру с namespace (`Rameva\` → `system/`, `App\` → `app/`, автозагрузка PSR-4).
2. PHP Guard во всех файлах `system/`, `app/`, `config/`: проверка константы, которая определяется только в bootstrap/`index.php`; при прямом обращении к файлу — немедленное завершение с явным кодом ответа (403 для «доступ запрещён», 404 там, где не нужно подтверждать существование файла) и **без** уникального текста вроде «Direct access denied» — сообщение не должно быть общим для всех инсталляций Rameva и превращаться в сигнатуру для массового сканирования. Ничего не должно возвращаться с кодом 200 при отказе в доступе.
3. Guard-заглушки (файл, отдающий 403 без листинга каталога) во всех подпапках, включая пока не защищённые внутри `system/` — Core, Helpers, Http, Rendering, Security, Services. Сейчас такая заглушка стоит только на верхнем уровне `system/`.
4. Единый bootstrap: один файл, который определяет Guard-константу, поднимает автозагрузку и вызывается из `index.php`. Никакой маршрутизирующей логики в самом `index.php` — только подключение bootstrap.
5. Роутер на основе `pages/`: сканирует структуру папок, строит белый список маршрутов, кэширует карту в `storage/cache/routes.php`. Запрос, не попавший в карту — уже признак подозрительного трафика (сама блокировка сканеров — задача следующего этапа, не этого прохода).
6. Разрешение страницы: есть `controller.php` (controller - имя страницы, совпададает с page) — подключить; есть `page.html` — взять как контент. Простейшую подстановку `{{ var }}` можно сделать сразу, если это не требует решений по SEO-модулям, но полноценное «слияние по тегам» с layout (см. ниже) в этот проход не входит.
7. Конфигурация — только PHP-массивы (`app/Config/*.php`), без `.env`-файлов: `.env` PHP не выполняет как код, поэтому Guard его не защищает, и при прямом запросе он отдаётся как обычный текст.

**В этот проход сознательно не входит** (следующие итерации): полноценный SEO-модуль (canonical/OpenGraph/Schema.org, генерация sitemap.xml и llms.txt из карты маршрутов), Request Intelligence Engine (allow/block-list по URI, ограничение частоты запросов), деконструкция под WordPress, Tripwire-мониторинг целостности ядра, система переопределения (`app/Pages` поверх системных страниц по умолчанию), обработка форм и писем. Их не нужно ни реализовывать, ни проектировать заранее — важно только не создавать в этом проходе структур, которые придётся ломать, когда до них дойдёт очередь.

**Слияние layout «по тегам» — зафиксировано для следующего прохода**, чтобы не изобреталось на ходу, если дойдёт раньше срока: если `page.html` — уже полный HTML-документ (есть `<html>`/`<body>`), рендер берёт только содержимое `<body>`; `<title>` и `<meta>` из `<head>` этого файла полностью игнорируются — вся метаинформация страницы должна приходить только из будущей системы генерации метаданных, а не из тегов, случайно оставшихся в загруженном файле.

## Правила работы для этого прохода

- Прежде чем массово переносить файлы, покажи предполагаемое сопоставление «старый файл → новое место» и дождись подтверждения — не переименовывай и не реструктурируй молча.
- Guard добавляется в файл сразу при его переносе, а не отдельным проходом после — так меньше риск забыть файл.
- Если старый код совмещает несколько обязанностей (например, класс одновременно рендерит и обращается к БД) — в этом проходе не рефактори это, просто перенеси и подключи; рефакторинг — отдельная, явно обсуждённая задача.
- Не создавай `.env`, не создавай `config/` вне `app/Config/`, не создавай отдельный каталог `public/` — структура уже задана и самостоятельно не меняется.
- Если по ходу переноса возникает архитектурный вопрос, которого нет в этом задании (например, как называть конкретный метод или куда класть конкретный сервис из старого ядра) — сначала спроси, не додумывай функциональность, которой не было в задании.

## Критерий готовности этого прохода

Сайт на `fw2.loc` открывает страницы из `pages/` через единственную точку входа `index.php`. Прямой HTTP-запрос к любому файлу внутри `system/`, `app/`, `config/` и к любой внутренней папке (включая ранее не защищённые подпапки `system/`) возвращает пустой ответ с кодом 403 или 404 без текста, который можно использовать как отпечаток Rameva. Перенесённые Router, Db, AntiBot, FormService, LogService, MailService, Canonical, Schema, Cache подключены под новыми namespace и не содержат исполняемого кода верхнего уровня вне объявления класса.
