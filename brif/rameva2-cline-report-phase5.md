## 1. Часть A — закрытие находок

### 1.1. Прямой доступ к внутренним каталогам

| Что | Файл | Проверка на живом сайте |
|---|---|---|
| Закрыт каталог шаблонов страниц | `public/pages/.htaccess` | `/pages/about.html` → **403** (было 200) |
| Закрыт каталог приложения | `public/app/.htaccess` | `/app/Layouts/main.html` → **403** |
| Закрыт каталог ядра | `public/system/.htaccess` | `/system/Layouts/default.html`, `/system/Boot.php` → **403** |
| `robots.txt` запрещает обход | `system/Services/RobotsGenerator.php` | в файле три `Disallow:` для `/pages/`, `/app/`, `/system/` |

`.htaccess` дописывает директивы **внутрь группы `User-agent: *`**: директивы robots.txt действуют только в пределах своей группы, поэтому дописывание в конец файла после чужой группы ограничило бы не тех роботов. Если группы `*` нет — создаётся новая группа в конце файла, правила конкретных роботов не затрагиваются. Строка `Sitemap` по-прежнему берётся из `siteurl`.

Аудит `pages/`, `app/Layouts/`, `system/Layouts/` на секреты: **чисто** (8 файлов, только шаблоны и guard-файлы; совпадений по `secret|password|token|api_key|smtp|dbname|@домен` нет). Конфигурация и секреты — только в `app/Config/*.php` (PHP Guard + закрытый каталог).

## 2. Что из инструкции я НЕ выполнил и почему

### 2.1. Предрендер `pages/*.html` в собственный отрендеренный вид — отказ

Предлагалось перезаписывать сам файл страницы её отрендеренным содержимым при компиляции карты маршрутов (для страниц без контроллера и без layout). Это вредно:

1. **Противоречит базовой модели проекта.** В `rameva2-cline-brief.md` (этап 1) зафиксировано: «Модель страниц — только runtime, без офлайн-компилятора… Отдельного шага “сборки” перед публикацией нет — это лишняя инфраструктура для одного разработчика и источник рассинхронизации между исходником и скомпилированным файлом». Предрендер — тот же build-шаг, только с потерей исходника.
2. **Уничтожает шаблон.** После первой перезаписи в файле не остаётся плейсхолдеров: страница перестаёт быть управляемой данными, layout и метаданные перестают на неё влиять. Откат — только из VCS.
3. **Замораживает SEO-данные домена в файл.** `meta`/canonical/OG/JSON-LD формируются из `siteurl` и текущего запроса. Отрендерив это в статику, которую веб-сервер отдаёт напрямую (в обход фреймворка), получим `canonical`/`og:url` одного домена внутри файла: при смене домена, http→https или зеркале это даст неверные канонические адреса — вред тому самому SEO, ради которого механизм и делался.
4. **Не решает заявленную задачу.** Канонический ответ — это layout (`<head>` с canonical/OG/JSON-LD плюс обёртка), а файл страницы — самостоятельный документ; `Renderer` вообще выбрасывает `<head>` страницы при сборке. Даже идеальный предрендер даст иное содержимое, чем маршрут.
5. **Запись в исходники из веб-запроса.** Компиляция карты маршрутов при `debug = true` (текущее значение) происходит на каждый запрос → появляется путь «HTTP → запись в `pages/`», риск повреждения файла при конкурентных запросах, постоянный churn `mtime` (а `SitemapGenerator` берёт из `mtime` дату `lastmod`), затирание правок.
6. **Сейчас неприменимо буквально:** обе страницы (`pages/index.*`, `pages/about.*`) имеют контроллеры, поэтому условие «нет контроллера и нет layout» не сработало бы ни для одной из них.

Сделано вместо этого (в том же смысле — «обезвредить прямой запрос»): запрет на уровне сервера (`.htaccess` в трёх каталогах — работает сразу на Apache/OSPanel; пример location-блока в `deploy/nginx/` — для Nginx, где `.htaccess` бессилен), `Disallow` в `robots.txt`, аудит содержимого каталогов.

**Оговорка, которую надо принять честно:** без доступа к конфигу сервера (типовой Nginx-хостинг) закрыть `/pages/*.html` из PHP невозможно — запрос к существующему файлу не доходит до фреймворка. Конструктивное решение только одно — вынести шаблоны из docroot, а это меняет заданную структуру и требует вашего решения.

### 2.2. Манифест: «нет манифеста» — тревога, а не тихая перебазировка

Буквальная реализация «при первом запуске без манифеста — построить манифест» даёт обход мониторинга: удалить `storage/integrity.manifest.php`, дождаться первой проверки (она молча примет текущее `system/` за эталон) и подменить ядро.

Реализовано: отсутствие/повреждение манифеста = статус `no_manifest` → запись в `integrity.log` + письмо администратору + код ответа `2`; тихой перебазировки нет. Манифест создаётся явной командой `cron.php?…&action=build` (шаг «при установке»), а в тексте тревоги прямо сказано, что делать. Если всё же нужен автозапуск при первом запросе — это две строки в `Tripwire::check()`, скажите.

### 2.3. Более мелкие отклонения

- `datePublished` вычисляется из `mtime` файла страницы, а не захардкожен.
- Ключ `integrity.token` оставлен заполненным (сгенерирован для fw2.loc), чтобы `cron.php` работал сразу; для прода генерируйте свой: `php -r "echo bin2hex(random_bytes(32));"`. Пустой ключ полностью закрывает точку входа (fail closed).
- `cron.php` поддерживает веб-вызов (`?key=…&action=…`) и CLI (`php cron.php КЛЮЧ action`) — CLI удобнее для отладки и для хостингов с php-cli в cron.
- Коды ответа `cron.php`: `200` — ok/built; `500` — расхождение/нет манифеста (чтобы cron-мейлер хостинга сам сообщал о проблеме); `403` — нет доступа или модуль выключен.

## 3. Часть B — Tripwire (контроль целостности `system/`)

### 3.1. Состав

| Файл | Назначение |
|---|---|
| `system/Security/Tripwire.php` | ядро контроля: `build()`, `check()`, фоновая проверка, обработка вызова cron, журнал, уведомление |
| `public/cron.php` | отдельная точка входа для внешнего расписания (не через `pages/`, до роутера) |
| `app/Config/Security.php` | секция `integrity`: `enabled`, `token`, `background_check`, `check_interval`, `notify_admin` |
| `storage/integrity.manifest.php` | эталонный манифест SHA-256 (генерируется, PHP-файл под Guard) |
| `storage/integrity.state.php` | время и результат последней проверки (генерируется) |
| `storage/logs/integrity.log` | отдельный журнал мониторинга (не смешивается с `app.log`) |

Принципы: область — только `system/` (39 файлов); автовосстановления нет; манифест — не открытый файл с хэшами, а PHP-файл под тем же Guard, что и конфигурация; хэши не считаются на каждый запрос.

### 3.2. Как работает

1. **Манифест.** `Tripwire::build()` рекурсивно обходит `system/`, считает SHA-256 каждого файла, пишет `storage/integrity.manifest.php` (пути относительные, `ksort` для стабильного diff, массив возвращается под Guard).
2. **Проверка.** `Tripwire::check()` сверяет файл за файлом: `changed` / `removed` / `added`; результат — `ok`, `mismatch` или `no_manifest`.
3. **cron.php.** Проверяется **до роутера** (отдельный файл, ядро и маршрутизация не запускаются — `Boot.php` получил флаг `RAMEVA_NO_AUTOLAUNCH`). Ключ сравнивается через `hash_equals` (сравнение с постоянным временем), при неверном — обычный `403` с пустым телом, без опознавательных признаков; неудачные попытки дополнительно троттлятся RateLimiter'ом (30/мин, блокировка 15 мин) и пишутся в `security.log`. При верном ключе — та же проверка, что и у фонового триггера, независимо от интервала.
4. **Фоновый триггер.** `Boot.php` после `kernel->launch()` вызывает `Tripwire::runBackgroundCheckIfDue()`: если `background_check` включён и интервал (`check_interval`, по умолчанию сутки) истёк — соединение с клиентом завершается (`fastcgi_finish_request()`, иначе `ob_end_flush()+flush()`, `ignore_user_abort(true)`) и проверка выполняется после отправки ответа. Блокировка через `flock` гарантирует, что одновременно идёт только одна проверка.
5. **Реакция на расхождение.** Запись в `storage/logs/integrity.log` (пишется первой: `LogService` троттлит записи с одного IP в пределах секунды, поэтому событие мониторинга не должно стоять в очереди после чужой записи, например `mail.log` от `MailService`) + письмо администратору (`Mail.admin_email`) через уже готовый `MailService`, с флагом отключения `notify_admin`.
6. **Состояние** (`integrity.state.php`) хранит время и итог последней проверки — по нему считается интервал; интервал не зависит от того, кто инициировал проверку.

### 3.3. Установка (порядок)

```
1. php -r "echo bin2hex(random_bytes(32));"          # ключ
2. записать его в app/Config/Security.php → integrity.token
3. php public/cron.php КЛЮЧ build                    # эталонный манифест
4. в планировщике хостинга (ISPmanager → «Планировщик CRON»):
   wget -q -O /dev/null "https://site.ru/cron.php?key=КЛЮЧ&action=check"
   (или: php /path/to/public/cron.php КЛЮЧ check)
5. после обновления ядра — повторить шаг 3
```

## 4. Находки и рекомендации (решать отдельно)

1. **Фоновый триггер и «без задержки ответа».** На этой площадке PHP работает как модуль Apache, `fastcgi_finish_request()` недоступен, поэтому соединение закрывается только в конце скрипта: клиент получает тело раньше, но `%{time_total}` включает время проверки. Замер: `/about` — 38.9 мс при полном пересчёте 39 файлов, то есть на текущем объёме влияние в пределах шума. Под PHP-FPM соединение закрывается сразу. Рекомендация: основной механизм — `cron.php` по расписанию (как и было в брифе), фоновый триггер — страховка для хостингов без планировщика.
2. **Свежая установка и `no_manifest`.** Пока манифест не создан, первая же проверка пишет тревогу и пытается отправить письмо (не чаще интервала). Это честный сигнал, но на чистой установке выглядит как шум — лечится порядком установки из §3.3.
3. **`LogService` троттлит записи с одного IP (1 c).** События мониторинга зависят от порядка записи, поэтому `integrity.log` пишется до вызова `MailService`. Порядок стоит сохранять и впредь.
4. **Статические 403 (`.htaccess`) наших заголовков не содержат** — их отдаёт веб-сервер; `X-Powered-By` там диктуется настройками Apache/PHP, а не фреймворком (сейчас Apache добавляет только `Server: Apache`).
5. **`Disallow` в `robots.txt` — только для роботов.** Реальное закрытие доступа дают `.htaccess`/Nginx; для Nginx-only хостинга `Disallow` — единственная работающая мера, пока не добавлен location-блок.
6. **`breadcrumbList()`.** Абсолютные URL нормализуются в `breadcrumb()`; в `breadcrumbList()` (готовый массив `itemListElement`) значения остаются «как передали». Если нужно единообразие — нормализуем и там (мелкая правка).
7. **Установщика в проекте нет.** «Ключ генерируется при установке, манифест строится при установке» реализовано шагами §3.3: писать секреты в конфиг и манифест из веб-запроса было бы хуже.
8. **Служебные файлы Tripwire** (`integrity.manifest.php`, `integrity.state.php`, `integrity.lock`) лежат в `storage/` — каталог закрыт `.htaccess`, плюс в самих PHP-файлах стоит Guard.

- проверки по слоям: `checkUserAgent()`, `checkScreen()`, `checkWebGL()`, `checkCanvas()`, `checkAudio()`, `checkFonts()`, `checkAutomation()`, `checkFeatures()`, `checkTiming()`, `checkBehavior()`, `checkConsistency()` — со штрафами (`addError`/`addWarning`), жёсткими блоками (`setHardBlock()`) и итоговой статистикой (`buildStats()`);
- **Proof-of-Work** (`checkProofOfWork()`, сложность в конфиге) — в Rameva 2 сейчас отсутствует;
- токен по набранному score (`generateToken($score)`, `hmacSign()`), `deriveSecret()`, `generateUid()`, `handleFail()`, `renderBlocked()`;
- в JS: MD5/XOR-упаковка, сборщики `colNavigator/colScreen/colTimezone/colWebGL/colCanvas/colFonts/colConnection/colCSS`, `detectAutomation()` (в том числе поиск `cdc_`/`$cdc` в объектах окна), `colStack()` — анализ стека вызовов (определение V8).

Что есть в Rameva 2: тонкий `AntiBot` (cookie `_ab_challenge`, HMAC-токен `timestamp:ip:hash`, инлайн-JS, `403` + `noindex`) и `AntiBotValidator` (проверяет только `elapsed` и наличие `canvas/webgl/audio`, сравнивает сумму с `minTrustScore`). Серверная часть урезана радикально — и относительно v5, и относительно старого `AntiBotValidator` (18.5 KB).

Рекомендация: если включать AntiBot всерьёз — переносить v5 (его `AntiBot.php` + его `challenge.js`), а не дописывать текущий каркас. Помнить о причине, по которой AntiBot выключен по умолчанию (`app/Config/Security.php`): JS-фингерпринтинг блокирует SEO-роботов и клиентов без JS.
